# 設計案: 差し戻し直後の再停止を捕まえる

- 起案: CC（project-c セッション）2026/09/17
- 起案の契機: owner 逐語「ストップフレーズのハーネス向け設計案を用意」（2026/09/17）
- 対象: `hooks/assertion_ground_truth/dispatch.py` のループガード
- 状態: **採択・2026/09/17 稼働**（裁定 E-20990101000099-3ba4 ＋ 補足裁定 E-20990101000100-0126、第2段 E-20990101000102-39a3・owner 裁定「A 即稼働」）

## 1. 問題（実測）

2026/09/16 のセッションで、差し戻された直後の応答が再び停止句で終わったのに、差し戻しが来なかった。

観測ログ `notes/stop_phrase_observations.log`:

```
400:2026-09-16T21:56:38  /home/user/projects/project-c  no  出します,めて出します   declare,negative
401:2026-09-16T21:57:26  /home/user/projects/project-c  no  まとめます,めます       declare,negative
```

400 行目の応答は差し戻された。401 行目はその書き直しで、別の停止句（「まとめます」）で終わっている。**検出はされたが差し戻されていない。**

owner の指摘はここから始まっている。逐語「いやそれだと『次は .ai への Task G 完了報告の起草に取りかかります。…まとめます。』この文がヒットしなかった理由何？」。ヒットはしていた。差し戻しが出なかっただけである。

## 2. 原因

`dispatch.py` は再走時に 97 を観測専用でしか走らせない。

```python
if data.get("stop_hook_active"):
    # 前回の block による再走。差し戻しは1回だけ（無限ループ防止）。
    path = os.path.join(checker_dir, OBSERVE_ONLY_CHECKER)
    if os.path.isfile(path):
        run_checker(path, msg, cwd, data, {"AGT_STOP_HOOK_ACTIVE": "1"})
    return
```

無限ループ防止としては正しい。だが「差し戻された直後にまた停止句で終わる」は最も起きやすい失敗であり、そこが構造的に素通りになっている。**1回の差し戻しで直る前提が実測と合っていない。**

## 3. 案の比較

| 案 | 内容 | 無限ループの risk | 実装量 | 判定 |
|---|---|---|---|---|
| A | 再走時も無条件に差し戻す | 高い（永久に往復しうる） | 小 | 不可 |
| B | 再走時は差し戻さず、次のユーザーターン冒頭で通知する | なし | 中 | UserPromptSubmit は既定30秒でキャンセルされ出力が捨てられる（CLAUDE.md「レビュー担当」節の実測）。担い手にできない |
| C | 連鎖回数を数え、上限まで差し戻す | 上限で止まる | 中 | **推奨** |
| D | 差し戻し文に declare 語彙の抜粋を載せ、書き直しでの再発を減らす | なし | 小 | C と併用する補助策 |

## 4. 推奨案（C＋D）の仕様

### 4-1. 連鎖回数の保持

`dispatch.py` が state ファイルを持つ。

- 置き場所: `${TMPDIR:-/tmp}/agt_stop_phrase_chain/<session 識別子>.txt`
- session 識別子: `transcript_path` の basename（拡張子を除く）。入力 JSON から得られ、セッション間で衝突しない
- 内容: 連鎖回数（整数）1行のみ
- 寿命: 24時間より古いファイルは実行時に削除する（同ディレクトリを走査）。セッション終了を検知する手段がないため時間で切る

### 4-2. 判定

```
stop_hook_active が偽:
    連鎖回数を 0 にリセットして、従来どおり全 checker を走らせる

stop_hook_active が真:
    連鎖回数を読む（無ければ 0。読めなければ判定不能）
    連鎖回数が判定不能、または 連鎖回数 >= max_chain（conf・既定 2）なら:
        従来どおり 97 を観測専用で走らせて return
    そうでなければ:
        97 だけを通常モード（AGT_STOP_HOOK_ACTIVE を渡さない）で走らせる
        FAIL が無ければ return（連鎖回数は増やさない）
        連鎖回数 += 1 を保存する
            保存できなければ差し戻さずに return
        差し戻す。文面は §4-3
```

加算と保存の順は、実装で次の2点を満たす形にした（完了報告 E-20990101000101-761a Task 1-5）。

- **連鎖回数を増やすのは実際に差し戻したときだけ**である。走らせる前に増やすと、停止句の無い再応答でも猶予を削り、次に停止句で終わったときの猶予を前倒しで失う（T4「連鎖は増えない」）。
- **連鎖回数を保存できないときは差し戻さない**。保存できないまま差し戻すと上限を数えられず、無限ループを止める手段が無くなる。state の故障でセッションを壊さない（fail-open）ことと、発火の向きを fail-closed に保つことを、ここで両立させている。連鎖回数を読めないとき（判定不能）も同じく発火しない側へ倒す。

97 以外の checker を再走時に走らせないのは従来どおりとする。**広げるのは停止句だけ**である。他の checker（path_exists 等）は1回の差し戻しで直る性質のものが多く、実測上の穴が観測されていない。

### 4-3. 差し戻し文（再走時）

1回目と同じ文では、同じ書き直しを誘発する。再走時は次を出す。

```
FAIL	stop-phrase	差し戻し後の応答が再び停止句で終わっている（検出句=<句> tier=<層>・連鎖<n>回目）。
書き直しではなく、宣言した作業をこのターンで実行すること。実行できないなら
〈停止の判断〉1〜6のどれに当たるかを 停止条件=N で明記する。
```

残りの猶予は知らせない。「次は差し戻さない」と書くと、猶予を使い切るまで書き直しを続ける誘因になる（裁定 E-20990101000099-3ba4 の .ai 条件）。条件数 1〜6 は cc/CLAUDE.md〈停止の判断〉の現行の列挙に合わせている。

### 4-4. 併用する補助策（D）

差し戻し文の末尾に、declare 層のうち**その応答で当たらなかった上位の語**を数個載せる案がある。書き直しで別の停止句を選ぶ事故（今回の「出します」→「まとめます」）を減らす。ただし語彙を列挙すると「その語を避けて同じ構造の文を書く」回避を誘発しうる。**採否は owner の判断を要する。**

## 4-5. 既存の仕組みとの関係（調査済み）

- `stop_phrase_block_followup.py` が「差し戻しの直後に CC が何をしたか」を transcript から追う。出力列に `followup_ts` `marker` `n_assistant` `tail` がある。**本案の効果測定はこのスクリプトで足りる**。`tail` に停止句が残っているかを見れば、連鎖の実態が分かる。観測ログへの列追加（§5 の検出）は、これで代替できるなら不要
- `projects/meta-harness/PROJECT_STATE.md` L54 に、停止句 checker の穴が2件記録されている。ひとつは発火窓（関門2・アンカー必須）で、これは `require_anchor=no` により解消済み。もうひとつは「末尾が依頼文＋fenced code block で終わる完了報告は declare/negative のいずれにも当たらず記録もされない」。**本案が扱う穴（再走時の素通り）はここに記載がなく、新規の可能性が高い**
- 同 L54 に「**checker・句リスト・conf は未変更——FAIL を出しうる checker の変更は稼働前に .ai 確認を要する**（`stop_phrase_enforce.conf` の定め・裁定 `E-20990101000044-fe34` §2・§4）」とある。`dispatch.py` は checker ではないが、**FAIL の出方を変える**以上、同じ扱いとするのが妥当である。本案の実装は .ai の確認を経てから行う

## 5. ガード評価（禁止事項の実装規律 1〜4）

- **予防**: 本案そのものが予防にあたる。差し戻しの連鎖上限という形で、停止句で終わる応答を実行前（ターン確定前）に押し返す
- **検出**: 観測ログに連鎖回数の列を足す。現在の5列（時刻・cwd・anchor・検出句・tier）に `chain=<n>` を加えると、差し戻しが効いた回と効かなかった回を機械的に数えられる。**この列がないと本案の効果を測れない**
- **独立検証**: 観測ログと transcript の突合。差し戻し文が出たターンの次の応答が停止句を含むかを別プロセスで数える

## 6. 実挙動テスト（採択時に必ず実施する）

`dispatch.py` に標準入力を与えて直接叩く。本番 conf を書き換えず、`AGT_STOP_PHRASE_CONF` と `TMPDIR` を一時ディレクトリへ向ける。

| # | 入力 | 期待 |
|---|---|---|
| T1 | stop_hook_active=false・停止句あり | 差し戻し（従来どおり）・連鎖=1 |
| T2 | stop_hook_active=true・停止句あり・連鎖=1 | 差し戻し（§4-3 の文面）・連鎖=2 |
| T3 | stop_hook_active=true・停止句あり・連鎖=2 | 差し戻さない・観測ログには残る |
| T4 | stop_hook_active=true・停止句なし | 無音・連鎖は増えない |
| T5 | stop_hook_active=false・停止句なし | 無音・連鎖=0 にリセット |
| T6 | state ファイルが書けない場所 | 無音で継続（fail-open）。セッションを壊さない |

T6 は fail-open とする。state ファイルの故障でセッションが止まる方が害が大きい。**発火の向きだけは fail-closed**（判定できないときは差し戻さない）で揃える。

## 7. 受容するリスク

- 連鎖上限 2 は経験則である。実測（本案の検出列）で足りなければ増やす
- 24時間で state を消すため、長時間セッションでは連鎖がリセットされうる。過小に数える方向であり、差し戻しが増える側には倒れない
- 停止句そのものが自然言語であり、語彙リストの網羅性は保証されない。本案は語彙の穴を塞ぐものではなく、**検出できた停止句を差し戻しに繋げる経路**を直すものである
